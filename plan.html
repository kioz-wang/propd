4 协议重设计 P1

4.1 Ctrl/IO 分离 — 设计上是正确的

结论: Ctrl=DGRAM + IO=STREAM 在 Unix domain 本机场景下是正确的设计选择。不需要改。DGRAM 无连接、天然有消息边界，适合一问一答的 management RPC。STREAM 适合多路复用数据流。

4.2 当前协议的核心问题

#问题表现
1手写序列化散落 4 处ctrl.c / unix.c / server/io.c / unix_stream.c 各自 pack/unpack
2无帧边界send/recv 裸用，server 必须精确知道"接下来多少字节"
3union dispatch 无法扩展加新消息类型要改 union 定义，影响所有已有分支

4.3 Codec 模块 — 零分配访问器

Codec 不是序列化引擎，而是类型安全的指针访问器集合。不引入额外 malloc。

// codec.h — 纯内联，零开销
struct ctrl_package {
    ctrl_type_t type;
    uint16_t    payload_len;
    uint8_t     name_len;
    char        name[];           // flexible
};

static inline struct register_child_payload*
ctrl_as_child(const struct ctrl_package *p) {
    assert(p->type == _ctrl_register_child);
    return (struct register_child_payload *)(p->name + p->name_len);
}

static inline const char*
ctrl_as_name(const struct ctrl_package *p) {
    return p->name;
}
核心价值: 把散落在 4 个文件里靠约定和指针算术维持的 pack/unpack 收敛到一个模块。内存分配次数不变（仍然只有一次 malloc → recvfrom）。

4.4 变长 PDU — 方案 A (最小改动)

定长 key[255]/name[255]/items[N][255] 是 96% 浪费的根源。加 _len 前缀即可解决。

新 IO 请求头

struct io_package {
    io_type_t   type;          // 1B
    timestamp_t created;       // 8B
    uint8_t     key_len;       // 1B  ← 变长
    uint32_t    value_len;     // 4B  (仅 set 时 >0)
    char        key[];         // key_len 字节
    // 后跟 value_len 字节数据
};
// get("/db/host"): 14+7 = 21B  (vs 269B, 效率 5.6% → 71%)

新 Ctrl 请求头

struct ctrl_package {
    ctrl_type_t type;          // 1B
    uint16_t    payload_len;   // 2B  显式长度
    uint8_t     name_len;      // 1B
    char        name[];        // 变长
};

// register_child payload:
//   uint8_t num_cache_now; uint8_t num_prefix;
//   for each: uint8_t len + str
//
// register_child("db", 1 cache, 2 prefix):
//   1+2+1+2 + 1+1 + 1+7 + 1+5 + 1+6 = 29B  (vs 1029B, 4% → 68%)
// unregister_child("db"):
//   1+2+1+2 = 6B  (vs 256B)

5 注册 / 反注册机制

问题严重度描述
组包/解包无封装 P1 每个 API 重复 ctrl_init → 填字段 → ctrl_update → ctrl_final0。register_child 自己写 ~25 行填充逻辑
解包无边界校验 P0 register_child() 直接用 child->num_prefix 遍历数组，未检查 (N+M)×255 ≤ recvfrom 收到的字节数
io_update 同步阻塞 P1 Ctrl worker 中 io_update() 连接子节点并等待响应，慢子节点卡住线程池
反注册 zombie 缺失 P1 nref > 0 直接 EBUSY。建议: zombie 标记，route_deref 自动清理

7 Append 模式 P1

新增 _ctrl_register_child_append (type=6)，包结构复用 ctrl_package_register_child_t。

模式注册名已存在注册名不存在
普通 (type=0)清理旧的，创建新的创建新的
追加 (type=6)追加 prefix / cache_now返回 ENOENT
# 启动时核心注册
prop ctrl register_child db-server /db/* /config/*

# 运行时热加载新模块
prop ctrl register_child_append db-server /metrics/* /health/*

不需要协议层分片；一次 append 装不下由调用方多次 append。

9 改进建议

统一 IO 响应 P0

struct io_response {
    int32_t     result;        // 4B
    timestamp_t duration;      // 8B  (非 get 时为 0)
    uint32_t    value_length;  // 4B  (0 = 无 value)
    uint8_t     value[];       // value_length 字节
};

handler 不再直接 send，所有输出由 worker 循环统一发送。

ENOMEM 也要 send result P0

if (!value) {
    logfE("no memory");
    int err = ENOMEM;
    send(connfd, &err, sizeof(err), MSG_NOSIGNAL);  // ← 新增
    /* discard client value data */
    return ENOMEM;
}

字段重命名 P0

当前 (误导)→ 建议
value_t value;value_type_t value_type; uint32_t value_length;

Ctrl 加 payload_length P1

struct ctrl_package {
    ctrl_type_t type;
    uint16_t    payload_length;   // ← 显式声明变长部分大小
    union { ... };
};

目标协议 v2 (远期)

// IO 请求 (变长)
struct io_request {

13 IO 分层 & TCP 演进

13.1 当前分层分析

server 侧一次 get 请求经过 4 个文件:

文件职责评价
io.c网络 I/O + 协议解析 (accept → recv → dispatch → send)保留, 但 handler 内 send() 需修复 → worker 统一 send
io_context.c业务逻辑编排 (cache → route → lock → storage)✅ 边界正确, 传输无关
storage.c仅日志装饰器, 99% 是 logfI + 转发函数指针太薄 — 建议移到 storage.h 作为 static inline
unix_stream.c通用 I/O 抽象 (us_read/us_write, 含帧边界处理)✅ 正确, client 已迁移, server 待迁移
计划: server io.c 也改用 us_t (原定, 未完成)。完成后 worker() 的 recv/send 替换为 us_read/us_write，顺带解决两个 P0: 响应不对称 (io_response 统一) 和 ENOMEM 不发 result。

13.2 TCP 就绪度

builtin/tcp.c 已有 client 侧骨架。加 TCP server 的关键分析:

模块状态加 TCP 需要的改动
io_context / route / cache✅ 完全传输无关零改动
storage_t 接口✅ client 侧已有 tcp stub实现 get/set/del (复用 unix.c 模式, 连 TCP 而非 UDS)
unix_stream (帧边界)⚠ client 已用, server 未迁移server io.c → us_t 迁移后, TCP 下帧边界天然成立
server/io.c (listener)❌ AF_LOCAL 硬编码抽象 listener: Unix/TCP 各实现 open/accept/close
server/io.c (auth)❌ SO_PEERCRED Unix 专属抽象 transport_auth: Unix→SO_PEERCRED, TCP→token/TLS
